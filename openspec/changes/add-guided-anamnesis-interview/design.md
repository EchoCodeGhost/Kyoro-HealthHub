## Context

This project has repeatedly benefited from AI-assisted anamnesis conducted as ad-hoc conversation (outside the app itself): mentioning a livestock-market visit before a pneumonia led to a Coxiella  exposure chain. None of this came from answering a fixed questionnaire — it came from an interviewer (human-in-the-loop LLM) that already knew which follow-up mattered and asked it.

`scripts/query/health_query.py` already establishes this project's multi-provider LLM pattern: a configured local backend (e.g. Llama3-Med42-70B on `localhost:8080`, see `llm_backends.md`) by default, keyword-based routing between a default and a "medical" backend, a `timeout: 0` convention for long local generations, and — via the same `health_config.json` mechanism — the option to configure a remote provider instead (OpenRouter, Anthropic, etc., see README's "External AI providers" section). This change reuses that provider dispatch rather than inventing a new LLM integration path, and does not hard-restrict itself to local-only: the user explicitly wants the option to point this specific tool at a stronger remote model (e.g. via OpenRouter) rather than being limited to whatever is locally hosted.

The interview happens over multiple sittings in reality — memories surface days apart — so the tool needs to persist partial progress locally, not just print a transcript to the terminal.

## Goals / Non-Goals

**Goals:**
- Reproduce the associative, cross-referencing interview style that produced real diagnostic leads in this project, as a reusable local tool.
- Support six interview tracks: exposure/travel history, animal contact history, family history, occupational history & exposures, leisure & hobbies, social history (tobacco/e-cigarette/other substance use and sexual history) — same underlying engine, track-specific opening prompts and extraction schema. Together these aim at a comprehensive life review ("Gesamt-Nabelschau"), not just infectious/genetic exposure.
- Reproduce the memory-anchored recall pattern that independently surfaced a real diagnostic lead (from describing childhood photos in detail) — proactively suggest physical memory aids (old photos, diaries/calendars, historical medical paperwork) as recall triggers, not just open verbal questions.
- Persist both the raw conversation and incrementally-extracted structured rows, resumable across sessions.
- Local-first, but not local-only: default to the local backend, while allowing the user to configure a remote provider (e.g. OpenRouter) for this tool the same way other query tools in this project already do — with an explicit warning surfaced before a session starts against a non-local provider, since this is arguably the most sensitive data category in the whole project (unfiltered family health disclosures, hard to pseudonymize without losing the associative value of the interview).
- Produce output usable both as human-readable review material  and eventually as importable rows for a future exposure-history-aware compute/analysis script.

**Non-Goals:**
- Not a replacement for a clinician taking a history — output is explicitly a discovery/preparation aid, not a diagnosis.
- Not building a general-purpose chatbot UI — CLI only for v1, consistent with the rest of `scripts/`.
- Not attempting automatic causal inference ("you have condition X because of exposure Y") — the tool surfaces and structures leads; a human (with or without a doctor) still evaluates them.
- Not covering non-German languages beyond the existing `t()`/`add_lang_arg` bilingual pattern already used project-wide.
- Not integrating with `compute_all.py`/`analyse_all.py` in this iteration — the new table is written and human/LLM-readable, but no derived-metric computation is proposed here.
- Not building image upload, OCR, or document/photo parsing — the memory-anchor mechanism (decision 8 below) is a *prompting* technique: the user is asked to go look at a photo or document and describe it in their own words as a normal conversation turn. Actual image/document ingestion is a materially larger feature (new upload surface, new sensitivity class for uploaded family photos/medical documents) and explicitly deferred.

## Decisions

**1. New script under `scripts/query/`, not a new top-level directory.**
Alternatives considered: a dedicated `scripts/anamnese/` directory. Rejected — the tool's defining characteristic is that it's an LLM-driven natural-language interaction against local data, which is exactly what `scripts/query/` already holds (`health_query.py`, `context_query.py`). Keeping it there means it inherits the existing provider-dispatch code path instead of duplicating it.

**2. Reuse `llm_provider.py`'s existing multi-provider dispatch, do not add a new "anamnesis" backend.**
The `medical` keyword-routed backend already exists for clinical topics. Interview prompts naturally contain medical keywords (symptom, diagnos, familienanamnese) and will route there already. Whatever provider is configured for that backend in `health_config.json` — local (Med42) or remote (OpenRouter, Anthropic, etc.) — is what the interview uses; no new backend config needed, no local-only restriction hardcoded into this tool. A remote-provider session SHALL trigger the one-time warning described in the proposal (reusing the README's existing "External AI providers" guidance: prefer ZDR, TLS, and now also VPN), because unlike most of this project's query traffic (metric values, SQL results), interview transcripts are unstructured personal narrative that cannot be meaningfully pseudonymized before sending without defeating the point of the associative interview.

**3. Six tracks, each with its own track-specific system prompt encoding the "cross-referencing" behavior, not a separate knowledge base.**
The two tracks added after initial scoping — occupational history & exposures (jobs, industries, chemical/solvent/dust/biological workplace exposure, shift-work patterns, workplace environment such as mold/sick-building issues) and leisure & hobbies (sports, crafts, substances, hobby-related environmental exposure) — deliberately exclude animal contact from their scope even where a hobby involves animals (e.g. horseback riding, beekeeping), since that stays in the existing animal-contact track; the leisure track's system prompt should explicitly redirect animal-contact mentions there rather than duplicate extraction logic across tracks.
A third track added later — social history (tobacco, e-cigarettes/vaping, other substance use, sexual history) — covers a standard clinical anamnesis domain (Sozialanamnese) the original five tracks left uncovered: infection-risk factors (hepatitis B/C, HIV, endocarditis) and cardiovascular risk from smoking. Its system prompt explicitly instructs factual, non-judgmental, non-counseling phrasing, since this domain carries more stigma risk than the others if the model's tone drifted into moralizing.
Alternatives considered: a curated exposure→pathogen lookup table (JSON) that the script queries and injects into the conversation deterministically. Rejected for v1 — building and maintaining an accurate epidemiological lookup table is itself a significant, error-prone undertaking (the FHIR LOINC-mapping work in this project already showed how easily an LLM can misstate a specific code/fact when asserting from memory; the risk is similar here). Instead, the system prompt instructs the model to draw on its own trained knowledge and *explicitly flag* when it's making a connection ("X is a known reservoir for Y — worth asking Z") so the human can independently verify anything before acting on it, mirroring how this project's own case documents already carry that caveat everywhere factual claims appear (`brief-infektologe-2026.md` etc.). Revisit a curated lookup table later only if false leads become a repeated practical problem.

**4. New table `anamnese_findings` (EAV-flavored, consistent with `measurements`), not free-text-only storage.**
Columns: `id, session_id, track, date_or_period, place_or_subject, event_text, relevance_note, person, created_at`. `track` distinguishes exposure/travel/animal/family/occupational/leisure/social. `person` follows the existing convention (`OWN_PERSON_ID` for all tracks except family history, which uses a free-text family member label — never a bare string literal in code). **Update since this decision was first written:** the project's `pseudonymize-device-person-identifiers` change (now archived) installs an `AFTER INSERT` trigger on every table with a column literally named `person` (`scripts/modules/db.py`), which automatically rewrites any plaintext value — including a family-member label like `"Mutter"` — to a deterministic pseudonym (`PER-XXXXXXXX`) via `identity_resolver.resolve_person()`. This table gets that behavior automatically, no special-casing needed; use `identity_resolver.resolve_display_name()` when rendering the human-readable export (see impact on tasks.md 4.1). This lets a future script query "all animal-track findings" the same way `measurements` is queried today, without a schema migration when a new track type is added.

**5. Session/transcript persistence via a second table `anamnese_sessions` (`id, track, started_at, last_updated_at, transcript_json, status`), not flat files.**
Alternatives considered: one JSON file per session in `imports/_inbox/`-style storage. Rejected — sessions need to be listable/resumable ("continue where I left off") and the project already keeps everything else in SQLite; a second storage mechanism just for this feature adds inconsistency for no real benefit. `transcript_json` stores the raw turn-by-turn conversation so a resumed session can rebuild context for the LLM; `anamnese_findings` stores only the extracted structured rows.

**6. Extraction happens incrementally, not only at session end.**
After each user turn, the script asks the LLM (same call or a lightweight follow-up call) to emit any newly-mentioned structured facts as a small JSON block, which gets upserted into `anamnese_findings` immediately. This is why an interrupted session doesn't lose everything — matches the `INSERT OR IGNORE` durability convention already used everywhere else in this project.

**7. Human review gate before anything is treated as fact.**
Every extracted row is written with an implicit "as stated by user in interview" provenance — nothing here is auto-promoted into `clinical.events`/config. A human still decides what's real enough to carry into an actual doctor's letter, same as every existing doctor's-letter document was hand-assembled after the fact.

**8. Memory-anchor prompting: proactively suggest physical recall aids, not just open verbal questions.**
Independently of the associative cross-referencing pattern (decision 3), a second real lead in this project came from describing childhood photos in detail (a physical sign visible in retrospect but never consciously registered as a symptom at the time). Track system prompts SHALL, where contextually appropriate for the period/topic being discussed, proactively suggest that the user consult a physical memory aid — old photo albums, diaries/calendars, or historical medical paperwork (doctor's letters, lab reports, childhood examination booklets/U-Heft, vaccination records, allergy passports) — and describe what it shows. This is a *prompting* technique, not a new storage/ingestion mechanism: the user types a free-text description of what they see, exactly like any other conversation turn; no image upload, OCR, or document parsing is built (see Non-Goals). Alternatives considered: a fixed checklist ("do you have an old photo album? a vaccination record?") asked once at track start. Rejected as the sole mechanism — the same lesson as decision 3 applies: a static prompt misses the *associative* timing (suggesting "check your vaccination record" is most useful right when the conversation reaches a relevant period/topic, not as a generic opener), though a track's opening message MAY still mention upfront which memory aids tend to be useful for that track, as a standing reminder.

**9. Explicit, per-call language directive — do not rely on the system prompt's own language or a single instruction stated once.**
This project's own English-language planning artifacts (this design doc, the codebase) create real language-drift pressure once an LLM is generating extended free text against that backdrop — observed directly during this change's own planning session (an assistant drifted from German into English mid-conversation while working heavily in these English documents, then self-corrected only once it was pointed out). An anamnesis interview is exactly the worst place for that failure mode: it is a long, free-text, emotionally sensitive conversation with a patient, not a short structured query. Mitigation: every LLM call for a session (the main turn-loop call in 3.4 AND the separate incremental-extraction call in 2.4) SHALL include an explicit language directive naming the session's configured language, not just a single instruction placed once at the start of the system prompt and assumed to hold. Alternatives considered: stating the language once in the opening system prompt only. Rejected — that is exactly the pattern that failed during this project's own planning work; a long conversation with many turns and a large accumulated transcript is precisely where a single early instruction loses influence over generation.

## Risks / Trade-offs

- **[Risk] LLM invents a plausible-sounding but wrong epidemiological connection ("X causes Y") and the user takes it at face value.** → Mitigation: system prompt requires the model to phrase connections as questions/hypotheses to verify, not assertions; every `anamnese_findings` row is explicitly framed as unverified interview output, consistent with decision 7.
- **[Risk] Sensitive family-member health disclosures get stored in a form that could later leak if the repo/DB is ever shared.** → Mitigation: this project's existing privacy rules already forbid diagnosis names/entity IDs in *source code*; this change does not touch that boundary (it's runtime data in `health.db`/`medicine.db`, same trust boundary as everything else already stored there), but the design doc calls out that `anamnese_findings.event_text` is free text and therefore the single highest-sensitivity field in the schema — flag this explicitly in the table's docstring/schema comment.
- **[Risk] If a remote provider is configured, unstructured personal/family health narrative leaves the machine — a materially bigger exposure than the structured metric values other query tools already send to remote providers.** → Mitigation: one-time explicit warning before starting a session against a non-local backend (spec requirement), reusing the project's existing external-AI-provider guidance (pseudonymize where possible, prefer ZDR providers, TLS, and now VPN per the README update); this is a user-accepted trade-off (stronger remote model vs. local-only privacy), not a silent default — local remains the default backend.
- **[Risk] Long local-model interviews are slow (large model, `timeout: 0`), making the tool feel sluggish compared to the ad-hoc chat experience that inspired it.** → Mitigation: this is exactly why a remote-provider option is offered as a user choice (decision 2) rather than enforcing local-only; users who prioritize speed/quality over the strictest privacy stance can opt into OpenRouter etc., same trade-off already offered by `health_query.py`.
- **[Risk] The LLM drifts out of the session's configured language (e.g. German) mid-interview**, especially over long conversations or when the underlying model has recently processed a lot of English-language content (a directly observed failure mode, not a hypothetical one — see decision 9). This is more disruptive here than in this project's other query tools because the interview is long-form and emotionally sensitive, not a single short exchange. → Mitigation: explicit, repeated per-call language directive (decision 9), not a single instruction at session start; dogfooding (task 6.5) SHALL specifically include a long, multi-turn session as a language-consistency check, not just a short smoke test.
- **[Risk] Track-specific prompt quality varies — each of the six tracks needs a different follow-up style, and getting one track's prompt wrong could produce a shallow interview.** → Mitigation: tasks.md should include manual dogfooding of each track against the author's own already-known history (where the "right" follow-ups are already known from this project's existing `intern/` documents) as an acceptance check, not just a synthetic test.
- **[Risk] Old medical paperwork (lab reports, doctor's letters) referenced via the memory-anchor prompting (decision 8) may contain numeric/clinical values the user transcribes imprecisely from memory or a quick glance.** → Mitigation: `anamnese_findings` rows are explicitly unverified interview output regardless of source (decision 7) — a value recalled from an old lab report is not more authoritative than a value recalled from memory alone, and should still go through the same human review gate before being treated as fact, not be silently upgraded in confidence because a document was involved.

## Migration Plan

Purely additive: new table creation via the existing `utils/create_schema.py` pattern (`CREATE TABLE IF NOT EXISTS`), new script, no changes to existing tables/scripts. No rollback complexity beyond removing the two new tables if abandoned.

## Open Questions

- Should extracted `anamnese_findings` rows eventually get a promotion path into `clinical.events` (config) or a dedicated `exposure_history` reporting view — deferred until real usage shows what's actually needed downstream.
- Whether family-history tracks need per-relative sub-identity handling (beyond a free-text `person` label) if this is ever extended to shared-access, multi-person use (`KYORO_ACTIVE_PATIENT_DIR` context) — out of scope for the single-user v1 described here.
